# Layout and manifests

A catalog is a directory containing a `catl.toml` file, any schemas it uses, and one directory per declared collection. Each collection contains its entities, either as individual manifest files or as directories with a manifest and companion files.

For example:

```text
clinical-catalog/
├── catl.toml
├── schemas/
│   ├── protocols.json
│   └── tools.json
├── protocols/
│   ├── triage.yaml
│   └── emergency-guide/
│       ├── manifest.yaml
│       ├── flow.md
│       └── diagram.png
└── tools/
    └── check-schedule.yaml
```

Here, `triage.yaml` is a flat entity with ID `triage`. The `emergency-guide` directory is a bundle entity with the same name as its ID. Both belong to the `protocols` collection.

## Directory layout

The catalog root is reserved for files and directories that `catl` knows about: `catl.toml`, `catl.lock`, declared collections, and schemas. An unexpected file or directory at the root fails validation.

Files and directories whose names start with a dot are ignored by both scanning and tree hashing. This is where you can keep things like editor settings, scratch files, or CI configuration without them becoming part of the catalog.

Catalogs can't be nested inside other catalogs. If you need multiple catalogs in the same repository, for example in a multi-tenant setup, keep them as siblings under a parent directory:

```text
registry.d/
├── catalog-a/
│   └── catl.toml
└── catalog-b/
    └── catl.toml
```

## Entity shapes

An entity is either a single manifest file or a directory containing a manifest and its companion files. The collection layout determines which one it is.

### Flat entities

A flat entity is a YAML or JSON manifest placed directly in the collection directory. Its filename, without the extension, is the entity ID.

```text
protocols/triage.yaml
```

The file contains the manifest itself:

```yaml title="protocols/triage.yaml"
title: Patient Triage Flow
severity: high
timeout_seconds: 300
```

Flat entities can't have companion files. If an entity needs images, Markdown documents, PDFs, or other assets, make it a bundle instead.

### Bundle entities

A bundle entity is a directory directly inside a collection. The directory name becomes the entity ID.

```text
protocols/emergency-guide/
├── manifest.yaml
├── flow.md
└── diagram.pdf
```

Every bundle must contain exactly one manifest, named `manifest.yaml` or `manifest.json`. Having both is an error.

The manifest describes the entity. All other files are companion files, and they can be organized into subdirectories as needed.

```text
protocols/emergency-guide/
├── manifest.yaml
├── steps/
│   ├── step-1.md
│   └── step-2.md
└── assets/
    └── flowchart.png
```

An entity can't be both flat and bundled. For example, `protocols/triage.yaml` and `protocols/triage/` can't exist in the same collection.

Subdirectories inside a collection aren't collections or categories. Every directory directly inside a collection is treated as a bundle entity, so entities can't be nested inside other entities.

## Manifest parsing

`catl` reads YAML or JSON manifests into memory before validating them against a schema.

YAML parsing follows YAML 1.2 core schema rules. Unquoted values like `yes`, `no`, `on`, and `off` are strings, not booleans; only `true` and `false` are parsed as booleans. Duplicate keys, merge keys (`<<`), and custom tags such as `!include` are rejected. A manifest must also contain exactly one document, so multiple documents separated by `---` aren't supported.

JSON manifests must follow RFC 8259 and use unique object keys. Numbers that evaluate to `NaN` or `Infinity` are rejected.

## Schema validation

Each collection can declare a JSON Schema Draft 2020-12 file in `catl.toml`. When a schema is configured, every manifest in that collection is validated against it.

Collections without a schema use permissive mode. Their manifests still have to be valid YAML or JSON and follow the catalog's layout rules, but `catl` doesn't check field types or other schema constraints. Bundle companion files are still hashed. However, validating a field with the `catl-file` format requires an explicit schema.

Here's a small example:

```json title="schemas/protocols.json"
{
    "$schema": "https://json-schema.org/draft/2020-12/schema",
    "type": "object",
    "required": ["title", "severity", "documentation"],
    "properties": {
        "title": { "type": "string" },
        "severity": {
            "type": "string",
            "enum": ["low", "medium", "high"]
        },
        "timeout_seconds": {
            "type": "integer",
            "minimum": 1
        },
        "documentation": {
            "type": "string",
            "format": "catl-file"
        }
    },
    "additionalProperties": false
}
```

Validation runs offline. `catl` embeds the Draft 2020-12 metaschema, so validating a manifest doesn't require network access.

Local `$ref` references can only resolve to files inside the catalog root. References that escape the root or point to remote URLs, such as `https://...`, are rejected. Absolute `$id` values declared in schemas don't change how local `$ref` references are resolved.

Schema regular expressions use Go's RE2 engine, which guarantees linear-time evaluation and avoids catastrophic backtracking (ReDoS). RE2 doesn't support every regex feature, though. Lookaround assertions such as `(?=...)` and `(?!...)`, along with backreferences, are rejected when the schema is compiled.

### The `catl-file` format

Use `"format": "catl-file"` on a string property when its value should point to a companion file inside a bundle.

```json
"documentation": {
  "type": "string",
  "format": "catl-file"
}
```

During validation, `catl` checks that the value is a relative path using forward slashes, with no leading slash or `..` segments, and that the referenced file exists inside the bundle directory. The format only works for bundle entities. Using it on a flat entity is a validation error because flat entities don't have companion files.

When `catl-file` appears inside a `oneOf` or `anyOf` schema, its constraints are checked only for the branch that successfully validates the manifest.

## Fixed limits

`catl` puts limits on input sizes and structure to keep memory use and validation time bounded, especially when reading untrusted catalogs.

| Target                  | Limit            | What happens     |
| ----------------------- | ---------------- | ---------------- |
| Identifier length       | 63 bytes         | Validation error |
| Relative path length    | 1,024 bytes      | Validation error |
| Path component length   | 255 bytes        | Validation error |
| Manifest file size      | 4 MiB            | Validation error |
| Schema file size        | 4 MiB            | Validation error |
| Decoded manifest values | 1,000,000 values | Parser error     |
| Manifest nesting depth  | 64 levels        | Parser error     |

The decoded-value limit also protects against excessive YAML alias expansion. These limits are enforced during parsing and validation, before oversized or deeply nested input can consume unbounded resources.
