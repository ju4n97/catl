# Layout and manifests

A catalog is a directory on disk containing a root `catl.toml`, schemas, and one directory per declared collection:

```bash
clinical-catalog/
├── catl.toml
├── schemas/
│   ├── protocols.schema.json
│   └── tools.schema.json
├── protocols/
│   ├── triage.yaml               # Flat entity: ID "triage"
│   └── emergency-guide/          # Bundle entity: ID "emergency-guide"
│       ├── manifest.yaml
│       ├── flow.md               # Companion file
│       └── diagram.png           # Companion image file
└── tools/
    └── check-schedule.yaml       # Flat entity: ID "check-schedule"
```

## Directory layout

The catalog root belongs exclusively to `catl`. Any unrecognized file or directory at the root that isn't a declared collection, schema folder, `catl.toml`, or `catl.lock` fails validation.

If you need scratch directories, editor settings, or CI scripts inside the root, prefix their names with a dot (`.`). Any file or folder starting with a dot is ignored by scanners and tree hashing.

Catalogs can't be nested inside other catalogs. To manage multiple catalogs in the same repository, keep them as sibling folders in a parent directory (like `my-registry/catalog-a/` and `my-registry/catalog-b/`).

## Entity shapes

Entities inside a collection take one of two shapes: flat files or directory bundles.

### Flat entities

A flat entity is a single manifest file placed directly in the collection directory. Its filename without the extension becomes its ID:

```text
protocols/triage.yaml
```

```yaml title="protocols/triage.yaml"
title: Patient Triage Flow
severity: high
timeout_seconds: 300
```

Flat entities can't have companion files. If an entity needs assets like Markdown templates, images, or PDFs, use a bundle instead.

### Bundle entities

A bundle entity is a directory placed directly inside the collection directory. The directory name is the entity ID:

```text
protocols/emergency-guide/
├── manifest.yaml
├── flow.md
└── diagram.pdf
```

A bundle must contain exactly one manifest named `manifest.yaml` or `manifest.json`. Having both in the same bundle is an error.

The manifest describes the entity, while any other files in the directory are companion files. Companion files can be organized in subdirectories:

```text
protocols/emergency-guide/
├── manifest.yaml
├── steps/
│   ├── step-1.md
│   └── step-2.md
└── assets/
    └── flowchart.png
```

An identifier can't be used as both a flat file and a bundle directory in the same collection. For example, `protocols/triage.yaml` and `protocols/triage/` can't coexist.

Directories inside a collection don't nest. Any subdirectory directly inside a collection is treated as an entity, not a category or sub-collection.

## Manifest decoding

Manifests are decoded into memory before schema validation using strict YAML 1.2 core schema rules or RFC 8259 JSON:

- Unquoted values like `yes`, `no`, `on`, and `off` are parsed as strings, not booleans. Only `true` and `false` are booleans.
- CRLF line endings (`\r\n`) are rejected. Manifests and schema files must use Unix LF line endings (`\n`).
- Duplicate keys are rejected.
- Merge keys (`<<`) are rejected.
- Custom YAML tags (like `!include` or `!custom`) are rejected.
- Multi-document streams separated by `---` are rejected. Each manifest file must contain exactly one document.
- JSON numbers must not evaluate to `NaN` or `Infinity`.

## Schema validation

Each collection can optionally point to a JSON Schema Draft 2020-12 file. When configured, every manifest in the collection is validated against it.

If `schema` is omitted in `catl.toml`, the collection operates in permissive mode: manifests are checked for syntax, unique keys, and layout rules, but field-level checks are skipped.

```json title="schemas/protocols.schema.json"
{
    "$schema": "https://json-schema.org/draft/2020-12/schema",
    "type": "object",
    "required": ["title", "severity", "documentation"],
    "properties": {
        "title": { "type": "string" },
        "severity": { "type": "string", "enum": ["low", "medium", "high"] },
        "timeout_seconds": { "type": "integer", "minimum": 1 },
        "documentation": { "type": "string", "format": "catl-file" }
    },
    "additionalProperties": false
}
```

Validation runs entirely offline. The Draft 2020-12 metaschema is embedded into `catl`, and validation never touches the network.

Local `$ref` references can only resolve to files inside the catalog root. References that escape the root or point to remote URLs (`https://...`) are rejected.

Regular expressions in schemas are evaluated using Go's RE2 engine. RE2 guarantees linear-time evaluation and eliminates catastrophic backtracking (ReDoS). Lookaround assertions (`(?=...)`, `(?!...)`) and backreferences are rejected during schema compilation.

### The catl-file format

A string property can specify `"format": "catl-file"` to verify that its value points to an existing companion file in the bundle:

```json
"documentation": {
  "type": "string",
  "format": "catl-file"
}
```

When validating this field, `catl` checks that:

- The value is a relative path using forward slashes without leading slashes or `..` segments.
- The file exists on disk inside the bundle directory.
- The entity is actually a bundle. Using `catl-file` on a flat entity is a validation error because flat entities have no companion files.

In schemas using `oneOf` or `anyOf`, `catl-file` assertions are checked only on the branch that successfully validates the manifest.

## Fixed limits

`catl` enforces fixed limits to keep memory consumption bounded when reading untrusted input:

| Target                  | Limit            | Behavior on breach                   |
| ----------------------- | ---------------- | ------------------------------------ |
| Identifier length       | 63 bytes         | Validation error                     |
| Relative path length    | 1,024 bytes      | Validation error                     |
| Path component length   | 255 bytes        | Validation error                     |
| Manifest file size      | 4 MiB            | Validation error                     |
| Schema file size        | 4 MiB            | Validation error                     |
| Decoded manifest values | 1,000,000 values | Parser error (alias expansion limit) |
| Manifest nesting depth  | 64 levels        | Parser error                         |
