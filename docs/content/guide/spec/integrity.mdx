# Integrity

`catl` uses deterministic tree hashing to identify catalog contents. Given the same included files with the same paths and bytes, it produces the same hash on Linux, macOS, and Windows.

The hash covers manifests, schemas, companion files, and other tracked-by-the-algorithm files. It doesn't include everything in the directory. Dot-prefixed paths and the root `catl.lock` are excluded.

## The tree hash algorithm

The tree hash is a SHA-256 digest of a sorted list of file hashes and paths. File contents are hashed as-is, while paths are normalized so the result doesn't depend on the operating system's path separator.

1. Scan the catalog root for regular files, skipping any file or directory whose path component starts with an ASCII dot (`.`), as well as the root `catl.lock`.
2. Reject paths containing ASCII control characters (`0x00`–`0x1F` or `0x7F`) or backslashes.
3. Normalize relative paths to use forward slashes, with no leading slash.
4. Hash each file's raw bytes with SHA-256 and format the digest as lowercase hexadecimal.
5. Sort the entries by path in byte-wise lexicographical order.
6. Build a payload with one line per file, using this format:

    ```text
    <hex-digest>  <path>\n
    ```

    That's the 64-character file digest, two spaces, the relative path, and a newline.

7. Hash the complete payload with SHA-256 and prefix the resulting digest with `sha256:`.

The file paths are part of the hash, not just the file contents. Renaming a file or moving it to another directory changes the tree hash, even when its contents stay the same.

When the payload is empty, the result is:

```text
sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
```

This is the SHA-256 digest of zero bytes.

## Line endings

Because tree hashes are calculated over raw file bytes, line endings affect the digest. A file with Windows CRLF line endings (`\r\n`) produces a different digest than the same file with Unix LF endings (`\n`).

To prevent silent hash divergence across platforms:

1. **Structured files strictly require LF:** `catl.toml`, `catl.lock`, collection schemas, and manifests reject CRLF line endings directly during validation.
2. **Git checkouts use LF:** `catl init` automatically writes `.gitattributes` to the catalog root:
    ```text
    * text=auto eol=lf
    ```

## Threat model

`catl` checks that catalog contents match the expected structure and recorded hashes. These checks catch several common problems:

| Threat                                          | Defense                                                            | When it's checked               |
| ----------------------------------------------- | ------------------------------------------------------------------ | ------------------------------- |
| An upstream Git tag moves                       | The resolved tree hash no longer matches the lockfile              | Dependency fetch and validation |
| A companion file in a dependency is modified    | Its tree hash differs from the recorded hash                       | Dependency fetch and validation |
| A vendored catalog is modified                  | `catl.Open()` checks its tree hash against `catl.lock`             | Catalog loading                 |
| A path escapes its intended root                | Paths are validated; invalid paths and `..` traversal are rejected | Catalog loading                 |
| Excessive YAML alias expansion                  | Decoded values are capped at 1,000,000                             | Manifest decoding               |
| A schema regex causes catastrophic backtracking | Go's RE2 engine provides linear-time regex evaluation              | Schema compilation              |

These checks help detect unexpected changes, invalid paths, and resource-exhaustion attempts. They don't replace every security control an application might need.

## Non-goals

**Cryptographic provenance:** A matching tree hash proves that the included file bytes match the expected digest. It doesn't prove who created or approved those files. For signed releases or trusted publishers, verify commit or release signatures separately with tools such as Sigstore or GPG.

**Runtime interpretation:** `catl` validates and loads data; it doesn't execute entity definitions, deploy infrastructure, or evaluate application-specific queries. The consuming application decides what the validated data means and what actions to take.

**Snapshot isolation for dirty working trees:** A filesystem is not automatically a snapshot of the entire catalog. If files change while an application is reading them, it can observe data from different points in time. Use a clean, immutable checkout or a verified vendor directory for production workloads.
