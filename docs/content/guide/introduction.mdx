# Introduction

`catl` is a package manager and data layer for declarative YAML and JSON data stored in directories.

A catalog is a directory tree containing `catl.toml`, schemas, and collections of entities. Entities are stored as standalone manifest files (flat entities) or as directories containing a manifest alongside companion files (bundles):

```text
catalog/
├── catl.toml                 # Catalog name, collections, and dependencies
├── catl.lock                 # Pinned dependency revisions and tree hashes
├── schemas/
│   └── service.schema.json   # JSON Schema Draft 2020-12
└── services/
    ├── auth.yaml             # Flat entity (ID: auth)
    └── billing/              # Bundle entity (ID: billing)
        ├── manifest.yaml     # Validated manifest
        ├── runbook.md        # Companion file
        └── diagram.png       # Companion file
```

`catl` is distributed as a standalone CLI and Go library. Both use the same parsing engine and validation rules.

## How it works

Collections and their schemas are declared in `catl.toml`. Manifests use strict YAML 1.2 or JSON syntax and are validated against JSON Schema Draft 2020-12.

Bundles keep structured manifests and their companion files together. The catalog computes a deterministic SHA-256 tree hash over all tracked files, so tampered files, moved Git tags, or line-ending divergences are detected immediately.

Catalogs can declare local directory paths and remote Git repositories as dependencies. Running `catl update` records the resolved 40-character commit hash and content tree hash in `catl.lock`. Dependencies are strictly direct and non-transitive; a dependency's own dependencies are ignored.

Validation runs locally and synchronously with zero network calls and no database. Schemas, dependencies, and companion files must already exist on disk, in `.catl/vendor`, or in the local cache. If a file is missing, a schema constraint is violated, or a tree hash doesn't match the lockfile, `catl` fails immediately.

## Why catl?

Reading YAML files from disk is simple. Keeping them valid, safe, and consistent across multiple applications is harder:

- Standard YAML 1.1 parsers silently coerce unquoted strings like `no` or `off` into booleans.
- Manifest parsers can't tell you whether a referenced companion file (such as a Markdown body, runbook, or image) actually exists on disk.
- Unchecked relative file paths can escape catalog boundaries via `../`.
- Detecting content drift across Linux, macOS, and Windows requires normalizing path separators and line endings before hashing.

`catl` handles validation, path safety, dependency locking, and integrity hashing in one place, allowing applications to read and query the data directly.

## Use cases

`catl` works anywhere structured data lives in Git and is consumed across different runtimes:

- **Service catalogs:** Keeping service ownership, tiers, and metadata alongside companion OpenAPI specifications or incident runbooks.
- **Headless CMS data layers:** Managing structured frontmatter alongside raw Markdown copy and image assets.
- **Feature-flag registries:** Versioning rollout rules in Git, queried with microsecond latency in Go or over HTTP.
- **Policy repositories:** Maintaining OPA/Rego policies, compliance rules, and test fixtures validated before deployment.
- **AI agent registries:** Managing prompt templates, system instructions, and tool definitions.
- Many more...
