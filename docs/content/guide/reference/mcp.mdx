# Model Context Protocol (MCP)

`catl` implements the [Model Context Protocol (MCP)](https://modelcontextprotocol.io), an open standard for connecting development tools and language models to verified local context.

The MCP server communicates over standard input/output (`stdio`) using the official [`github.com/modelcontextprotocol/go-sdk`](https://github.com/modelcontextprotocol/go-sdk). It exposes catalog entities and bundle companion files as **MCP Resources** and verification routines as **MCP Tools**.

```bash
# Run MCP server for a single catalog
catl mcp ./compliance-catalog

# Run MCP server for a multi-tenant registry directory
catl mcp ./registry.d
```

## Client configuration

`catl` can be connected to any MCP-compatible client that supports the `stdio` transport.

Configure your client to launch `catl` with the `mcp` command and the path to your catalog:

```bash
catl mcp /absolute/path/to/catalog
```

For a multi-tenant registry, provide the registry directory instead:

```bash
catl mcp /absolute/path/to/registry.d
```

In your client's MCP server settings, register `catl` as a local **stdio server**, using `catl` as the command and the relevant path as an argument following `mcp`. Ensure `catl` is available on the client's `PATH`, or specify the full path to the executable.

Refer to your corresponding client's documentation for its configuration format and instructions.

## MCP Resources

All catalog manifests and companion files are mapped to read-only URI resources under the `catl://` scheme.

### Resource URI syntax

| Target             | URI Pattern                                       | MIME Type                                                         |
| :----------------- | :------------------------------------------------ | :---------------------------------------------------------------- |
| **Manifest**       | `catl://{collection}/{qualified_id}/manifest`     | `application/yaml` or `application/json`                          |
| **Companion file** | `catl://{collection}/{qualified_id}/files/{path}` | Inferred from file extension (e.g. `text/markdown`, `text/plain`) |

### Examples

- `catl://services/platform.auth/manifest`
- `catl://services/platform.billing/files/runbook.md`
- `catl://monitors/network.latency/manifest`

When a client requests `resources/list`, `catl` returns all manifests and companion files discovered across active collections. When a resource is read via `resources/read`, the server streams the content directly from memory.

## MCP Tools

The server registers tools for discovery, inspection, and dry-run validation:

### 1. `catl_list_collections`

Lists all declared collections across active catalogs along with their current entity counts.

- **Parameters:** None (`{}`)
- **Returns:**
    ```json
    {
        "collections": [
            {
                "catalog": "platform",
                "name": "services",
                "entity_count": 4
            }
        ]
    }
    ```

### 2. `catl_list_entities`

Returns a formatted inventory of entities across all collections, or filtered by collection name.

- **Parameters:**
    - `collection` (string, optional): Restrict output to a specific collection (e.g. `services`).
- **Returns:**
    ```json
    {
        "entities": [
            "services\tplatform.auth\tsvcs/auth.yaml",
            "services\tplatform.billing\tsvcs/billing/manifest.yaml"
        ]
    }
    ```

### 3. `catl_get_entity`

Retrieves the complete entity resource representation, including identity metadata, companion file listing, and parsed manifest content.

- **Parameters:**
    - `collection` (string, required): Collection name (e.g. `services`).
    - `qualified_id` (string, required): Canonical entity identifier (e.g. `platform.billing`).
- **Returns:** Full JSON entity envelope with unmarshaled manifest fields.

### 4. `catl_get_schema`

Retrieves the raw JSON Schema Draft 2020-12 definition configured for a collection. Use this to inspect valid fields, types, and constraints before generating or editing manifests.

- **Parameters:**
    - `collection` (string, required): Collection name (e.g. `services`).
    - `catalog` (string, optional): Required only in multi-catalog registries to disambiguate.
- **Returns:**
    ```json
    {
        "catalog": "platform",
        "collection": "services",
        "permissive": false,
        "schema": "{\"$schema\": \"https://json-schema.org/draft/2020-12/schema\", ...}"
    }
    ```

### 5. `catl_read_file`

Reads an individual companion file (such as a runbook, documentation, or template) from a bundle entity.

- **Parameters:**
    - `collection` (string, required): Collection name (e.g. `services`).
    - `qualified_id` (string, required): Qualified entity identifier (e.g. `platform.billing`).
    - `path` (string, required): Relative path inside the bundle (e.g. `runbook.md`).
- **Returns:**
    ```json
    {
        "path": "runbook.md",
        "mime_type": "text/markdown",
        "text": "# Billing Runbook\n..."
    }
    ```

### 6. `catl_validate_manifest`

Dry-run validates an uncommitted YAML or JSON manifest string in memory against a collection's configured schema without touching the filesystem.

- **Parameters:**
    - `collection` (string, required): Target collection name.
    - `content` (string, required): Raw YAML or JSON manifest text.
    - `catalog` (string, optional): Required in multi-catalog registries.
- **Returns:**
    ```json
    {
        "valid": false,
        "diagnostics": [
            {
                "path": "services/manifest.yaml",
                "line": 3,
                "pointer": "/threshold",
                "message": "150 is greater than the maximum of 100"
            }
        ]
    }
    ```

### 7. `catl_check`

Validates that all catalog manifests conform to collection schemas and verifies path invariants and content tree hashes.

- **Parameters:** None (`{}`)
- **Returns:**
    ```json
    {
        "valid": true,
        "tree_hash": "sha256:7b2817c991e01cbe5d7500d4d0c8c7ecba12b516d4b7dd7c60e31b38978ffc77",
        "summary": [
            "Catalog \"platform\" valid. Content hash: sha256:7b28... (4 entities)"
        ]
    }
    ```

## Operational modes

- **Single-catalog mode:** Active when target directory contains `catl.toml`. Resources are scoped directly to that catalog's namespace.
- **Registry mode:** Active when target directory contains multiple catalog subdirectories (e.g. `registry.d/`). All tenant catalogs are served simultaneously without identifier collisions.

## Embedding in Go

Go applications can embed `catlmcp` directly using the official SDK:

```go
package main

import (
	"context"
	"log"

	"github.com/modelcontextprotocol/go-sdk/mcp"

	"github.com/ju4n97/catl"
	"github.com/ju4n97/catl/catlmcp"
)

func main() {
	ctx := context.Background()

	cat, err := catl.Open(ctx, "./catalog", catl.Options{Offline: true})
	if err != nil {
		log.Fatalf("failed to open catalog: %v", err)
	}

	srv := catlmcp.New(cat)

	// Run over stdio transport
	if err := srv.Run(ctx, &mcp.StdioTransport{}); err != nil {
		log.Fatalf("mcp server error: %v", err)
	}
}
```
