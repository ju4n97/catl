# Quick start

This guide walks through building a data layer for a Git-backed CMS. You'll define a schema, add articles and companion assets, catch validation errors without going online, and query the catalog through the CLI.

## Why use catl?

Reading YAML files from Git sounds simple. You can load them with `os.ReadFile` and parse them, but that is just a small part. Once the content is used in production, you also need to validate it, keep file references from breaking, and make sure different tools interpret it the same way.

For example, some YAML 1.1 parsers treat unquoted values like `no`, `on`, and `off` as booleans. A country code such as `country: no` can end up with the wrong type. Parsers in different programming languages can also disagree, which makes it harder to keep validation consistent across your Go backend, Python scripts, and frontend.

Then there are companion files. An article might reference `cover.png` or a bundle might contain an OpenAPI spec, but parsing the manifest doesn't tell you whether those files actually exist. File paths need validation too, so content can't reference files outside the intended directory. And if you need to verify that a catalog hasn't changed, you need a deterministic way to hash its contents across different operating systems.

`catl` handles these checks in one place. You define schemas, validate manifests, check references to companion files, and compute deterministic tree hashes. Your application can focus on the editing UI, publishing workflow, and rendering instead of reimplementing the data layer.

## Use cases

A CMS is a convenient way to see how `catl` works, but the same model applies anywhere structured data lives in Git.

You can use it for service catalogs that keep ownership metadata and OpenAPI specs together, feature-flag registries that version rollout rules, or policy repositories that validate OPA/Rego policies before deployment. It also works for AI agent registries that store prompt templates, system instructions, tool definitions, and many other use cases.

The core idea is to keep structured data in files, define what those files should look like using JSON Schema, and validate them before the application uses them.

<Steps>

### Create a catalog

Scaffold a new catalog using `catl init`:

```bash
catl init --name blog --collection articles blog-cms
cd blog-cms
```

The command creates the catalog configuration, a starter schema, and line-ending attributes:

```text
create blog-cms/catl.toml
create blog-cms/schemas/articles.schema.json
create blog-cms/.gitattributes
```

`catl.toml` binds the `articles` collection to its schema:

```toml title="catl.toml"
[catalog]
name = "blog"

[collections.articles]
schema = "schemas/articles.schema.json"
```

### Define the content schema

Replace `schemas/articles.schema.json` with this definition:

```json title="schemas/articles.schema.json"
{
    "$schema": "https://json-schema.org/draft/2020-12/schema",
    "type": "object",
    "required": ["title", "author", "published", "reading_time_minutes"],
    "properties": {
        "title": { "type": "string" },
        "author": { "type": "string" },
        "published": { "type": "boolean" },
        "reading_time_minutes": {
            "type": "integer",
            "minimum": 1
        },
        "cover_image": {
            "type": "string",
            "format": "catl-file"
        }
    },
    "additionalProperties": false
}
```

This enforces four required properties, requires `reading_time_minutes` to be at least 1, and rejects unrecognized fields (`additionalProperties: false`).

The `"format": "catl-file"` constraint on `cover_image` tells `catl` to verify that the value points to an existing companion file inside the entity bundle. If the path leaves the bundle or the file doesn't exist, validation fails.

### Author content

Entities inside a collection take one of two shapes: flat files or directory bundles.

**Flat entity: Standalone announcement**

Create `articles/welcome.yaml`. The filename without its extension becomes the entity ID (`welcome`):

```yaml title="articles/welcome.yaml"
title: Welcome to the new blog
author: Editorial Team
published: true
reading_time_minutes: 1
```

Flat entities are single manifest files. They can't contain companion assets.

**Bundle entity: Article with companion Markdown and images**

When content requires companion files (such as Markdown copy, diagrams, or cover images), create a directory named after the entity ID:

```bash
mkdir -p articles/release-v1
```

Create the manifest (`manifest.yaml`):

```yaml title="articles/release-v1/manifest.yaml"
title: Launching version 1.0
author: Engineering
published: true
reading_time_minutes: 4
cover_image: banner.svg
```

Add the companion files inside `articles/release-v1`:

```markdown title="articles/release-v1/body.md"
# Launching version 1.0

Today we are releasing our core platform. All services are live.
```

Create an SVG placeholder for the banner image:

```xml title="articles/release-v1/banner.svg"
<svg xmlns="http://www.w3.org/2000/svg" width="100" height="100"><rect width="100%" height="100%" fill="#000"/></svg>
```

The manifest stores structured metadata for filtering and indexing, while `body.md` and `banner.svg` are companion files tracked by the catalog.

### Validate the catalog

Run `catl check` from the catalog root:

```bash
catl check
echo "Exit code: $?"
```

```text
Exit code: 0
```

`catl check` follows the Unix rule of silence: it exits with code 0 and produces no output when everything passes.

To see how `catl` enforces constraints, edit `articles/release-v1/manifest.yaml` and reference an image that doesn't exist:

```yaml
cover_image: missing.png
```

Run validation again:

```bash
catl check
```

```text
articles/release-v1/manifest.yaml:5: /cover_image: file "missing.png" not found in bundle
```

`catl` reports the file, line number, JSON pointer, and error reason, then exits with code 1. Revert `cover_image` back to `banner.svg` before continuing.

### Query and stream content

List all entities in the catalog:

```bash
catl list
```

```text
articles	blog.release-v1	articles/release-v1/manifest.yaml
articles	blog.welcome	articles/welcome.yaml
```

Entities are printed in tab-separated columns (`COLLECTION  QUALIFIED-ID  PATH`). Every entity is identified by its qualified ID: `namespace.id`.

Locate a manifest on disk using `catl resolve`:

```bash
catl resolve articles blog.release-v1
```

```text
articles/release-v1/manifest.yaml
```

Lookups strictly require both the collection name and the qualified ID. If you pass a bare ID without a namespace, `catl` rejects it with a hint:

```bash
catl resolve articles release-v1
```

```text
catl: "release-v1" is not a qualified ID (want namespace.id); did you mean "blog.release-v1"?
```

Stream raw manifest contents to stdout using `catl show`:

```bash
catl show articles blog.welcome
```

```yaml
title: Welcome to the new blog
author: Editorial Team
published: true
reading_time_minutes: 1
```

For bundle entities, pass the relative path of a companion file to stream its contents directly to stdout:

```bash
catl show articles blog.release-v1 body.md
```

```markdown
# Launching version 1.0

Today we are releasing our core platform. All services are live.
```

This output can be piped directly into Unix utilities, Markdown renderers, or static site generators.
